# 阶段3-平台抽象与适配（S3-T4）

> 范围：`pal/` 与 `platforms/` 的整体边界规则与落地方法  
> 目标：输出可复用判定规则（>=10 条）+ 实战判定样例，作为阶段3结项文档。

---

## 1. 阶段3总收敛

- **PAL（`pal/`）**：平台能力抽象与实现主体（web/native/minigame/runtime 分支）。  
- **Adapter（`platforms/*`）**：宿主环境接入与运行时桥接底座（`window/document`、`__globalAdapter`、`fsUtils`、`CCWebAssembly` 等）。  
- 二者关系是“**能力实现层（PAL）依赖运行时桥接层（Adapter）**”，不是二选一替代。

---

## 2. 统一分层模型

## 2.1 PAL 三层

1. **契约层**：`@types/pal/*.d.ts`（接口定义）  
2. **分发层**：`cc.config.json -> moduleOverrides`（构建期路由）  
3. **实现层**：`pal/*/(web|native|minigame|runtime)`（能力落地）

## 2.2 Adapter 两层

1. **宿主注入层**：`platforms/*/wrapper/builtin`、`unify.js`、`fs-utils.js`、`jsb-adapter/*`  
2. **运行补丁层**：`platforms/*/engine/*`、`common/engine/*`

---

## 3. 模块-职责-关键文件-边界判定

| 模块 | 职责 | 关键文件 | 边界判定 |
| --- | --- | --- | --- |
| PAL 契约 | 定义统一能力接口 | `@types/pal/*.d.ts` | 契约不等于实现 |
| PAL 分发 | 构建期选择实现分支 | `cc.config.json` | 以最终映射文件定责 |
| PAL 实现 | 系统信息/屏幕/输入/音频/env/pacer/wasm | `pal/system-info/*`、`pal/screen-adapter/*`、`pal/input/*`、`pal/audio/*` 等 | 主逻辑在 PAL 即归 PAL |
| Native Adapter | JSB 环境注入与桥接 | `platforms/native/builtin/index.js`、`platforms/native/engine/index.js` | 提供底座，不替代 PAL |
| Minigame Adapter | `__globalAdapter`/`fsUtils`/Web API 垫片 | `platforms/minigame/platforms/*/wrapper/*` | 负责接宿主 API 与全局注入 |
| Runtime Adapter | Oppo/Vivo/Huawei 快游戏链路 | `platforms/runtime/platforms/*`、`bin/adapter/runtime/*` | 与 minigame 平行的一条适配线 |

---

## 4. 边界判定规则（12 条）

1. **看导入路径**：若上层导入 `pal/*`，优先判定 PAL 能力域。  
2. **看映射归宿**：以 `cc.config.json.moduleOverrides` 最终目标文件为准。  
3. **看目录职责**：`@types/pal` 仅定义契约，不承担平台实现。  
4. **看平台分支**：同模块在 `web/native/minigame` 均有实现，说明 PAL 主导实现。  
5. **看运行时注入**：`window.__globalAdapter`、`window.fsUtils`、`CCWebAssembly` 属于 Adapter 注入物。  
6. **看调用方向**：PAL 调 Adapter 注入能力正常；Adapter 不直接等价于 PAL 实现。  
7. **看文件类型**：`platforms` 多为 JS wrapper/builtin/engine，PAL 主体多为 TS。  
8. **看完整性校验**：存在 `checkPalIntegrity` 的模块通常是 PAL 契约实现链。  
9. **看触发链路**：模板 `game.ejs/index.ejs` `require('./web-adapter')`/`engine-adapter` 是启动接入点，不是 PAL 能力实现点。  
10. **看排障层级**：能力异常先定位 PAL 分支，再回查 Adapter 注入是否缺失。  
11. **看平台归属**：`oppo/vivo/huawei` 快游戏多在 `platforms/runtime`，别误判到 `platforms/minigame`。  
12. **看主逻辑位置**：即使依赖注入，若核心逻辑在 PAL 文件，归属仍是 PAL。

## 5. 典型判定样例

## 样例A：小游戏键盘输入异常

- 判定流程：`pal/input/minigame/*` -> `platforms/minigame/.../unify.js` 键盘桥接 -> `common/engine/Editbox.js`。  
- 结论：PAL 输入能力 + Adapter 桥接缺一不可，但功能归属仍在 PAL 输入模块。

## 样例B：native 分辨率刷新异常

- 判定流程：`pal/screen-adapter/native/screen-adapter.ts` -> `jsb.onResize` -> `platforms/native/builtin/jsb-adapter/window.js` 的 `window.resize`。  
- 结论：PAL 负责屏幕能力抽象；Adapter 提供 resize 事件落地。

## 样例C：WASM 初始化失败（小游戏）

- 判定流程：`pal/wasm/wasm-minigame.ts` -> `CCWebAssembly/fsUtils` 全局对象 -> `platforms/minigame/.../builtin/index.js` 与 `fs-utils.js`。  
- 结论：根因多在 Adapter 注入缺失，但故障定位入口仍应从 PAL wasm 分支开始。
