- No optimization is retained after a crash, rendering regression, D3D12 validation error, or measurable FPS regression.
- Instancing is outside the current optimization scope.

## Measurement protocol

- FPS source: successful D3D12 swapchain presents measured over wall-clock intervals and logged as `[D3D12-FPS]`.
- FPS logging cadence: approximately once per second, never once per frame.
- Warm-up/readiness: startup, shader compilation, initial resource upload, splash-screen samples, and the long loading interval are excluded. Slow initial loading is expected and is never classified as an optimization failure.
- Readiness gate from Round 25 onward: first observe the slow-load marker (`intervalMs >= 3000` or `fps < 10`), then collect exactly `30` subsequent `[D3D12-FPS]` entries as a readiness-only warm-up window. Those 30 entries are never included in the result.
- Formal sample gate from Round 25 onward: only after all 30 readiness entries exist, collect the next exactly `30` consecutive `[D3D12-FPS]` entries as the formal window. Fewer than 30 readiness entries or fewer than 30 formal entries is `not ready`, never a performance failure.
- Slow-load waiting: startup duration does not fail a run while the exact process remains alive and no crash/D3D12 error is present. The monitor waits up to 15 minutes per launch, reports an incomplete window as `not ready`, and never substitutes splash/loading entries for missing readiness or formal samples.
- Comparison: use the same executable configuration, scene, window state, readiness rule, and 30-sample count.
- Contention control: from round 14 onward only `test-cases.exe` is launched at Windows `High` priority because round 13 proved sustained unrelated CPU load. The immediately adjacent reverted round-13 A/B result (`23.365` FPS) is the new comparison baseline; absolute values from earlier normal-priority runs are not mixed with this series.
- Baseline supplied by user: 2-3 FPS originally; approximately 10 FPS after the preceding optimization round. A fresh measured baseline is pending.

## Round 21 ExecuteCommandLists-scoped buffer-state epoch

Additional direct submission sites remain conservative and are out of this performance correction unless runtime evidence requires them.
- Gate before behavior change: a focused static test must require the non-empty-list check before `ExecuteCommandLists`, one epoch advancement after that call and before the fallible fence signal, and no epoch advancement in `acquire()`. ## Round 8 bounded two-frame submission batch

- Root-cause evidence: steady diagnostics measured a 15-19 ms fence wait at every `acquire()`. The command buffer had one allocator/list, and the device globally reset shader-visible descriptor pools and upload pages, so simply removing the wait would reuse resources still referenced by the GPU.
- Safety closure: two command recording contexts preserve allocator/list and retained-resource lifetime independently. Descriptor and upload pools remain append-only for exactly two frames; before frame three, the latest batch fence is awaited and only then are all batch allocations reset. This bounds transient memory while avoiding in-flight reuse.
- State correctness: the non-boundary frame retains explicit `GENERIC_READ -> COPY_DEST` buffer barriers; only a completed batch advances the buffer-state epoch and uses D3D12 COMMON-state decay. Diagnostic counters alternate between approximately 5016 and 2512 barrier calls as expected.
- RED/GREEN: the new static test failed before implementation and the complete suite passed 33/33 afterward.
- Build: the authoritative `test-cases.sln` `Debug|x64` build passed. An initial 10-second orchestration timeout was invalid and was rerun successfully with a 120-second window; it was not treated as a compiler result.
- Correctness: a 22-second D3D12 Debug Layer plus perf-diagnostic run stayed alive with zero matched D3D12/allocator/barrier errors (`d3d12_perf_records/round-08/d3d12_perf_round08_debug_stdout.log`).
- Formal result: a 45-second D3D12 run with both diagnostics disabled produced a last-ten average of `19.31` FPS, range `19.15-19.43`, with zero matched errors (`d3d12_perf_records/round-08/d3d12_perf_round08_stdout.log`). Relative to round 7's immediate `16.61` reference, this is a `16.3%` gain; average frame time fell from about `60.2` to `51.8` ms.

## Round 10 constant-time command-list resource retention

- Decision-gating diagnostic: `flushPendingBufferUpdates()` drains once per steady frame with `pendingBuffersDrained=2502` and `maxPendingBufferBatch=2502`; the frame performs 2506 DEFAULT uploads in total. This proves the dominant updates arrive as one batch (`d3d12_perf_records/round-10/d3d12_perf_round10_diag_stdout.log`).
- Deeper root cause: before each timed upload section, `retainCommandListResource()` linearly searched the growing retained-resource vector. With roughly 2500 unique resources, duplicate detection performed about `2502 * 2501 / 2 = 3,128,751` pointer comparisons per frame in Debug STL. This cost was outside `defaultBufferUploadUs`, explaining a large portion of the previously unaccounted frame time.
- Minimal change: preserve the COM-owning vector exactly as before, but add an `unordered_set<ID3D12Resource *>` solely for constant-time duplicate detection. Both vector and set are stored per command recording context and released only after that context's fence completes.
- RED/GREEN: the focused check failed before implementation; after correcting a test-scope mistake (signature text is outside the helper's extracted function body), the complete static suite passed 35/35.
- Build: the authoritative `test-cases.sln` `Debug|x64` build passed.
- Formal result: a 45-second D3D12 run with diagnostics disabled produced a last-ten average of `23.19` FPS, range `23.01-23.42`, with zero matched errors (`d3d12_perf_records/round-10/d3d12_perf_round10_stdout.log`). Relative to round 9's `19.94`, this is a `16.3%` gain and about `7.0` ms lower average frame time.
- Correctness: a 20-second D3D12 Debug Layer run stayed alive with zero matched D3D12/allocator/barrier errors (`d3d12_perf_records/round-10/d3d12_perf_round10_debug_stdout.log`).
- Decision: retain. The diagnostic also proves batched barriers for the 2502-buffer drain are a justified next optimization, but it is not mixed into this round because resource retention and barrier batching are independent behavioral changes.
